Architecture 3-tiers – L2 Informatique 3
1. Introduction
Dans un projet informatique, écrire du code ne consiste pas seulement à faire fonctionner un
programme. Il faut aussi organiser ce code de manière claire, logique, maintenable et évolutive.
Une mauvaise organisation rend les corrections difficiles, provoque des duplications, augmente les
erreursetcompliqueletravailfutur.Unebonneorganisation,aucontraire,permetdecomprendre
rapidement le projet, d’ajouter de nouvelles fonctionnalités plus facilement et de séparer les
responsabilités de chaque partie du système.
L’architecture3-tiers est une manière classique et pédagogique d’organiser une application
informatique. Elle repose sur trois couches principales :
— le frontend, qui gère l’interface avec l’utilisateur;
— le backend, qui traite la logique métier et les échanges;
— la base de données, qui stocke les informations de manière persistante.
Cette architecture est particulièrement adaptée à l’apprentissage, car elle oblige à distinguer
clairement :
— ce que l’utilisateur voit;
— ce que le programme décide;
— ce que le système mémorise.
2. Objectifs pédagogiques
À l’issue de cette méthodologie, l’étudiant doit être capable de :
— comprendre le rôle de chaque tier dans une architecture 3-tiers;
— organiser ses dossiers et fichiers de manière cohérente;
— séparer l’interface utilisateur, la logique métier et les données;
— écrire un mini-projet structuré selon une architecture claire;
— comprendre le trajet d’une requête depuis l’utilisateur jusqu’à la base de données;
— préparer une base solide pour des projets plus complexes.
3. Principe général de l’architecture 3-tiers
Une architecture 3-tiers répartit les responsabilités sur trois niveaux distincts.
3.1. Tier 1 : le frontend
Le frontend est la partie visible de l’application. Il permet à l’utilisateur de :
— saisir des informations;
— consulter des données;
— déclencher des actions;
— recevoir des réponses du système.
Il contient souvent :
— des pages HTML;
— des feuilles de style CSS;
— du JavaScript pour l’interactivité.
Architecture 3-tiers – L2 Informatique 4
3.2. Tier 2 : le backend
Le backend reçoit les demandes du frontend, applique les règles du métier, contrôle les
données, dialogue avec la base de données et renvoie une réponse.
Il contient souvent :
— des routes ou contrôleurs;
— des services métier;
— des validations;
— des accès aux données.
3.3. Tier 3 : la base de données
La base de données conserve durablement les informations du système :
— utilisateurs;
— produits;
— commandes;
— notes;
— emprunts;
— stocks;
— etc.
Elle contient généralement :
— des tables;
— des relations;
— des contraintes;
— des requêtes SQL.
4. Pourquoi cette séparation est importante
La séparation en trois tiers apporte plusieurs avantages :
1. Clarté : chaque partie a un rôle précis.
2. Maintenance : on peut modifier l’interface sans réécrire toute la logique métier.
3. Évolutivité : on peut faire évoluer la base ou le backend sans toucher toute l’application.
4. Réutilisation : plusieurs interfaces peuvent utiliser le même backend.
5. Sécurité : le frontend n’accède pas directement à la base de données.
5. Règles générales d’organisation du code
Avant même d’écrire les fichiers, il faut respecter quelques principes simples.
Architecture 3-tiers – L2 Informatique 5
5.1. Une responsabilité principale par fichier
Chaque fichier doit avoir un rôle principal. Par exemple :
— une page pour afficher;
— un script pour gérer une action;
— un fichier SQL pour créer les tables;
— un service pour une logique métier précise.
5.2. Nommer clairement les dossiers et les fichiers
Les noms doivent être courts, explicites et cohérents. Il faut éviter des noms vagues comme :
test.js, data2.php, newfinalfinal.sql.
5.3. Éviter le mélange des rôles
Une même page ne doit pas :
— afficher l’interface;
— écrire directement du SQL;
— contenir toute la logique métier;
— faire de la validation complexe;
— gérer tous les cas du projet.
5.4. Centraliser les éléments réutilisables
Par exemple :
— les styles communs dans un dossiercss/;
— les scripts partagés dansjs/;
— les connexions BD dans un module unique;
— les fonctions métier dans des services.

7. Méthodologie d’organisation du frontend
7.1. Rôle du frontend
Le frontend ne doit pas contenir toute l’intelligence du système. Son rôle principal est de :
— afficher les informations;
— capter les actions de l’utilisateur;
— envoyer les données au backend;
— afficher les réponses reçues.
7.2. Organisation recommandée
Le frontend peut être organisé comme suit :
— pages/ : les pages ou écrans;
— css/ : les styles;
— js/ : les scripts;
— assets/ : images, icônes, logos.
Architecture 3-tiers – L2 Informatique 7
7.3. Règles de bonne pratique
— séparer le HTML, le CSS et le JavaScript;
— éviter le style directement dans les balises HTML;
— éviter les scripts trop longs dans une seule page;
— utiliser des fonctions JavaScript courtes et bien nommées;
— centraliser les appels API dans un fichier spécifique.

8. Méthodologie d’organisation du backend
8.1. Rôle du backend
Le backend constitue le cerveau logique de l’application. Il :
— reçoit les requêtes;
— valide les données;
— applique les règles métier;
— dialogue avec la base de données;
— renvoie une réponse structurée.
8.2. Organisation recommandée
Une organisation simple et pédagogique du backend peut distinguer :
— routes/ : définissent les URL;
— controllers/ : gèrent la requête et la réponse;
— services/ : appliquent les règles métier;
— repositories/ : accèdent aux données;
— config/ : configuration générale, connexion BD.
8.3. Logique de circulation interne
Le trajet conseillé est le suivant :
Frontend → Route → Controller → Service → Repository → Base de données
Puis le chemin inverse pour la réponse.

un simple stockage improvisé. Elle doit refléter le domaine étudié avec clarté.

10. Cycle complet d’une requête
Pour bien comprendre l’architecture 3-tiers, il faut suivre le trajet d’une action.
10.1. Exemple : ajout d’un ouvrage
1. l’utilisateur saisit le titre et l’auteur dans le frontend;
2. le JavaScript envoie une requête HTTP au backend;
3. la route reçoit la requête;
4. le controller extrait les données;
5. le service vérifie que les champs sont valides;
6. le repository exécute la requête SQL;
7. la base enregistre la ligne;
8. le backend renvoie un message de succès;
9. le frontend affiche la confirmation.

Utilisateur → Frontend → Backend → Base de données→ Backend → Frontend → Utilisateur

13. Conventions de codage recommandées
13.1. Côté frontend
— noms de fichiers explicites;
— fonctions courtes;
— séparation HTML / CSS / JS;
— gestion propre des messages d’erreur.
13.2. Côté backend
— une route par ressource ou domaine;
— un controller par domaine principal;
— un service par logique métier;
— un repository par entité importante.
13.3. Côté base de données
— noms stables des tables;
— types adaptés;
— contraintes explicites;
— scripts séparés pour la création et les données d’exemple.

14. Erreurs fréquentes à éviter
1. écrire du SQL directement dans le frontend;
2. mettre toute la logique dans un seul fichier backend;
3. mélanger validation, accès BD et réponse HTTP au même endroit;
4. dupliquer les requêtes SQL;
5. ne pas séparer les scripts de création de base et les scripts de test;
6. utiliser des noms de fichiers non significatifs;
7. ne pas documenter la structure du projet.

18. Conclusion
L’architecture 3-tiers constitue une excellente base méthodologique pour apprendre à orga-
niser du code de manière professionnelle. Elle oblige à séparer ce que l’utilisateur voit, ce que le
système décide et ce que la base conserve. Pour un étudiant de deuxième année, cette architec-
ture offre un cadre clair pour comprendre comment construire un projet maintenable, évolutif
et cohérent.
L’essentiel n’est pas seulement de faire fonctionner l’application, mais de montrer que chaque
partie du code a une place logique. Un bon projet 3-tiers est un projet dans lequel on peut
répondre facilement aux questions suivantes :
— où se trouve l’interface?
— où se trouve la logique métier?
— où se trouve l’accès aux données?
— comment une requête circule-t-elle dans le système?
Annexe – Checklist rapide
— Les dossiers frontend, backend et database sont-ils distincts?
— Le frontend fait-il seulement l’affichage et l’interaction?
— Le backend est-il séparé en couches internes?
— Les requêtes SQL sont-elles centralisées?
— La base de données contient-elle des clés et contraintes?
— Le flux complet a-t-il été testé?
— Les noms des fichiers sont-ils explicites?
— Le projet est-il compréhensible par un autre lecteur?
