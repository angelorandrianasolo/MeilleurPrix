1  Contexte et Justification 
 
1.1  La problématique 
À Madagascar, les gens achètent et vendent leurs produits dans des marchés locaux appelés 
bazary. Le problème, c'est que ni les vendeurs ni les acheteurs ne savent vraiment comment 
les prix évoluent d'un jour à l'autre, ni si un autre marché propose le même produit moins cher 
alors que la majorité des femmes comparent les prix avant d’acheter et parfois certaine 
perdent beaucoup de temps et certaine n’arrive même pas acheter et rentrent sans rien 
acheter car elles ne trouvent pas les prix qui les conviennent. 
 
Voici les problèmes concrets observés : 
• Un vendeur fixe son prix au hasard parce qu'il n'a pas d'information sur les 
tendances du marché. 
• Un acheteur ne sait pas quel marché est le moins cher pour un produit donné. 
• Les prix varient beaucoup selon les saisons, les récoltes ou les événements locaux. 
• En zone rurale, la connexion internet est souvent coupée, ce qui rend difficile l'accès 
aux informations. 
• Les données de prix disponibles sont souvent incomplètes ou incorrectes. 
 
1.2  Pourquoi ce projet est important 
Ce projet propose de créer un système informatique capable de collecter les prix dans 
plusieurs marchés malgaches, d'analyser leurs tendances et de prédire leur évolution. 
L'objectif est d'aider les vendeurs et les acheteurs à prendre de meilleures décisions. 
 
En 2035, avec l'amélioration progressive de la couverture mobile à Madagascar, un tel 
système devient réalisable, même dans des zones avec une connexion limitée.  
 
 
2.  Objectifs du Projet 
 
2.1  Objectif principal 
Créer un système numérique qui collecte l es prix des produits dans différents marchés 
malgaches, les analyses, prédit leurs évolutions et aide les utilisateurs à décider où et quand 
acheter ou vendre. 
 
2.2  Objectifs secondaires 
• Collecter et stocker les prix de produits dans plusieurs marchés (Antananarivo, 
Toamasina, Fianarantsoa...). 
• Permettre de rechercher rapidement un produit par son nom. 
• Afficher les tendances et prévisions de prix sous forme de graphiques. 
• Trouver automatiquement le marché le moins cher pour un produit donné. 
• Faire fonctionner l'application même sans connexion internet (mode hors-ligne). 
• Proposer une interface en français et en malagasy. 
 
3.  Périmètre du Projet 
 
Ce que le projet inclut 
• Un module pour saisir et consulter les prix des produits. 
• Un module de recherche rapide de produits (par nom ou catégorie). 
• Un module de prévision des prix (analyse des tendances historiques). 
• Un module de comparaison des prix entre différents marchés. 
• Une interface web simple, accessible sur mobile et ordinateur. 
• Un mode hors-ligne avec synchronisation automatique quand la connexion revient. 
• Une interface disponible en français et en malagasy. 
 
4.  Analyse des Besoins 
 
4.1  Besoins fonctionnels  
• Recherche de produits : trouver rapidement un produit en tapant son nom. 
•  Affichage des tendances : voir l'historique des prix et la prévision des prix.

5.  Description Détaillée des Fonctionnalités  
 
Fonctionnalité 1 : Saisie et collecte des prix 
 
Titre Saisie des prix 
Description L'utilisateur entre le prix d'un produit dans un marché. Si internet est 
absent, la saisie est sauvegardée localement et envoyée au serveur 
dès que la connexion revient. 
Données manipulées Nom du produit, nom du marché, prix, date de saisie, unité (kg, litre...) 
Acteurs concernés Vendeur, Collecteur de données 
Résultats attendus Le prix est enregistré. Une file d'attente (queue) gère l'ordre d'envoi 
quand la connexion revient. 
Contraintes techniques Fonctionne sans internet (offline -first) ; données compressées pour 
économiser le débit ; saisie validée (prix > 0) 
 
Fonctionnalité 2 : Recherche de produits 
 
Titre Recherche de produits 
Description L'utilisateur tape les premières lettres d'un produit et voit apparaître 
des suggestions instantanément, sans attendre le serveur. La 
recherche fonctionne en français et en malagasy. 
Données manipulées Nom du produit (FR et MG), catégorie (légume, fruit, céréale...) 
Acteurs concernés Acheteur, Vendeur, Collecteur 
Résultats attendus Liste de suggestions qui apparaît dès 2 caractères tapés. Résultat en 
moins de 100 ms. 
Contraintes techniques Structure Trie implémentée à la main pour indexer les noms de 
produits ; supporte les caractères malagasy (UTF-8) 
 
Fonctionnalité 3 : Prévision des prix 
 
Titre Prévision de l'évolution des prix 
Description Le système analyse l'historique des prix d'un produit et prédit son prix 
pour les 30 prochains jours. On compare la méthode simple (moyenne 
 
 
basique) avec la méthode améliorée (moyenne mobile pondérée par 
programmation dynamique). 
Données manipulées Historique des prix (série de dates + valeurs), paramètres de fenêtre 
temporelle 
Acteurs concernés Acheteur, Vendeur 
Résultats attendus Un graphique avec la courbe historique et la prévision. Tableau 
comparatif : solution simple vs solution optimisée. 
Contraintes techniques Algorithme de fenêtrage glissant ; programmation dynamique pour les 
pondérations ; gestion des valeurs manquantes par interpolation 
 
Fonctionnalité 4 — Comparaison entre marchés 
 
Titre Trouver le marché le moins cher 
Description Les marchés sont représentés comme les points d'un réseau (graphe). 
L'algorithme de Dijkstra calcule le meilleur marché en tenant compte à 
la fois du prix du produit ET du coût pour s'y rendre. 
Données manipulées Liste des marchés (nom, ville, coordonnées), routes entre marchés 
(distance, coût transport), prix par produit par marché 
Acteurs concernés Acheteur 
Résultats attendus Affiche le marché optimal avec le prix final (produit + transport). Temps 
de calcul affiché pour montrer l'efficacité. 
Contraintes techniques Algorithme de Dijkstra codé manuellement avec un tas binaire (min -
heap) ; graphe stocké par listes d'adjacence 
 
Fonctionnalité 5 — Optimisation du panier d'achats 
 
Titre Optimiser les achats selon un budget 
Description L'utilisateur indique son budget et la liste de produits qu'il souhaite 
acheter. L'algorithme calcule quelle combinaison de produits et de 
marchés lui donne le maximum de valeur sans dépasser son budget. 
C'est une variante du problème du sac à dos. 
Données manipulées Budget de l'utilisateur, liste de produits souhaités avec leur importance, 
prix par marché 
Acteurs concernés Acheteur 
Résultats attendus Recommandation : quels produits acheter, dans quel marché, pour 
quel montant. Comparaison avec l'achat naïf (premier prix trouvé). 
Contraintes techniques Programmation dynamique (variante sac à dos 0/1) codée 
manuellement ; complexité O(n × Budget) 
 
Fonctionnalité 6 : Tableau de bord 
 
 
 
Titre Statistiques et indicateurs clés 
Description Un écran résumé affiche les informations les plus importantes : 
produits les plus chers, marchés les plus actifs, tendances générales. 
Les statistiques sont mises à jour sans tout recalculer depuis le début. 
Données manipulées Tous les prix enregistrés, statistiques agrégées (moyenne, min, max) 
Acteurs concernés Administrateur, Collecteur 
Résultats attendus Tableau de bord avec les top -5 produits/marchés, graphiques de 
tendance. Mise à jour en temps quasi-réel. 
Contraintes techniques Algorithme de maintien d'agrégats glissants (streaming) ; Fenwick tree 
pour les requêtes d'intervalle ; top-k par tas

8.  Contraintes 
 
8.1  Contraintes techniques liées au réalisme 2035  
Contrainte 1 — Connectivité intermittente 
En 2035, certaines zones restent sans réseau stable. 
• Solution architecturale : mode hors-ligne avec SQLite local + file d'attente de 
synchronisation. 
• Solution algorithmique : queue FIFO pour gérer l'ordre d'envoi des données en 
attente. 
 
Contrainte 2 — Faible débit réseau (2G/3G) 
Les transferts de données doivent être les plus petits possible. 
• Solution architecturale : données compressées, pagination des résultats, cache local. 
• Solution algorithmique : index Trie pour la recherche locale (pas d'appel serveur), 
agrégats glissants pour éviter de re-télécharger tout l'historique. 
 
Contrainte 3 — Données bruitées et incomplètes 
Les prix saisis à la main sur le terrain peuvent être faux, manquants ou aberrants. 
• Solution algorithmique : filtrage des valeurs aberrantes par fenêtre glissante, 
interpolation des données manquantes, validation des saisies. 
 
Contrainte 4 — Multilingue Français / Malagasy 
L'application doit être utilisable par des personnes ne parlant pas français. 
• Solution architecturale : système de traduction avec fichiers de langues séparés. 
• Solution algorithmique : le Trie supporte les caractères malagasy . 
8.2  Contraintes organisationnelles 
• Projet individuel : tout est réalisé par moi seul. 
• Durée limitée à 3 mois. 
• Les algorithmes doivent être codés manuellement, pas juste appelés depuis une 
bibliothèque. 
8.3  Contraintes de sécurité 
• Les mots de passe sont stockés de manière sécurisée . 
• L'accès à l'API est protégé par un token JWT. 
• Les données saisies sont vérifiées avant d'être enregistrées. 
 
8.4  Contraintes matérielles (accessibilité) 
• L'application doit fonctionner sur un smartphone Android basique (pas besoin de 
dernier modèle). 
• Taille de texte lisible, contraste suffisant pour une utilisation en plein soleil.
